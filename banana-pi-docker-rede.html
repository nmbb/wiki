Quando o Docker arrancou antes da rede

Diário de uma avaria · Laboratório em produção

O servidor estava online.
Os serviços, não.

Após uma interrupção elétrica e o posterior arranque do Banana Pi, o Docker aparecia como ativo, mas vários containers estavam parados. O erro não estava no disco cheio, no próprio Docker, nem obrigatoriamente nas aplicações. Faltava um detalhe: o endereço IPv4 ainda não existia quando o Docker tentou publicar algumas portas.

1. Um arranque aparentemente normal

O Banana Pi M5 é um servidor ARM com Armbian e Docker, ligado à rede de servidores (VLAN 40). Entre os serviços alojados estão Mosquitto, Zigbee2MQTT, Uptime Kuma, SmokePing, phpIPAM (web, cron e MariaDB) e Homarr. O Zigbee2MQTT comunica através da rede com um coordenador Zigbee noutra VLAN.

Na madrugada de 13 de novembro de 2026, após perturbações no fornecimento elétrico e novos arranques, vários desses serviços não estavam disponíveis. Foi possível entrar por SSH no Banana Pi e verificar que o sistema operativo e o motor Docker estavam ativos.

Energia / arranque→Armbian→Ethernet + DHCP→Docker→Containers

A primeira verificação mostrou o sistema ligado há cerca de 22 minutos, a partição principal de aproximadamente 15 GB com 35% de utilização e o serviço Docker com estado active e arranque enabled. Portanto, nem falta de espaço nem Docker completamente desligado explicavam a falha.

2. O diagnóstico começou pelos comandos mais simples

Confirmar o sistema e os containers

uptime
df -h
systemctl is-active docker
systemctl is-enabled docker
docker ps -a --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"

Depois, verificaram-se as políticas de reinício:

docker ps -aq | xargs -r docker inspect \
  --format '{{.Name}} | restart={{.HostConfig.RestartPolicy.Name}}'

Resultado: todos os oito containers apresentavam restart=unless-stopped. Isto é importante, mas não significa que todas as dependências externas já estejam disponíveis no instante em que são iniciados.

Consultar o erro gravado pelo Docker

docker ps -aq | xargs -r docker inspect \
  --format '{{.Name}} | exit={{.State.ExitCode}} | error={{.State.Error}} | finished={{.State.FinishedAt}}'

Três containers mostravam praticamente o mesmo erro, mudando apenas o nome e a porta. Exemplo com o phpIPAM (endereço de publicação substituído para proteger a rede real):

driver failed programming external connectivity on endpoint phpipam-web:
Error starting userland proxy:
listen tcp4 10.10.40.20:8083:
bind: cannot assign requested address
Não confundir dois erros diferentes: cannot assign requested address significa que o sistema não conseguia utilizar aquele endereço local no momento do bind. Não é o mesmo que address already in use, que normalmente indicaria uma porta ocupada por outro processo.

Verificar se o endereço existe e quem gere a rede

ip -br addr
ip route
systemctl is-active systemd-networkd
systemctl is-active NetworkManager
systemctl is-active systemd-networkd-wait-online
networkctl status end0

O resultado foi esclarecedor: systemd-networkd estava ativo, NetworkManager inativo, e o systemd-networkd-wait-online tinha falhado. Mais tarde, a interface física end0 já mostrava estado routable (configured), online, 1 Gbps e o IP esperado obtido por DHCP a partir da firewall.

Ou seja, a rede estava boa na altura da inspeção. O problema terá ocorrido mais cedo, durante o arranque.

3. A causa provável: a rede chegou depois do Docker

O registo do serviço de espera mostrou que o Armbian estava a tentar aguardar pela rede durante 20 segundos, mas terminou com falha. O Docker tinha, na sua unidade, as dependências After=network-online.target e Wants=network-online.target. Estas diretivas ajudam a ordenar o arranque; contudo, não obrigam o Docker a desistir se o serviço de espera pela rede falhar.

systemd-networkd-wait-online --any --timeout=20
# Resultado observado no primeiro arranque:
# status=1/FAILURE
  1. 1 · Sistema iniciaO Armbian começa a arrancar os serviços do sistema.
  2. 2 · DHCP ainda não terminouA interface end0 ainda não tem o IPv4 específico de que alguns containers precisam.
  3. 3 · Espera pela rede falhaO serviço de verificação esgota os 20 segundos previstos.
  4. 4 · Docker tenta publicar portasOs containers com 10.10.40.20:PORTA falham com cannot assign requested address.
  5. 5 · Rede fica operacional mais tardeO endereço aparece na interface, mas os serviços que já falharam podem continuar parados.

Esta sequência é a explicação mais consistente com os registos recolhidos. Não foi capturada a cronologia completa de todos os eventos do boot, pelo que não se pode atribuir automaticamente o mesmo erro ao Zigbee2MQTT ou ao Mosquitto.

Porque é que o Homarr continuou a funcionar?

O Homarr tinha a porta publicada em 0.0.0.0:7575, o endereço genérico que escuta nas interfaces disponíveis. Já o phpIPAM, o SmokePing e o Uptime Kuma estavam configurados com um endereço IP específico. Esta diferença ajuda a explicar os sintomas, embora não seja uma razão para expor indiscriminadamente todos os serviços em 0.0.0.0.

O facto de o endereço ser fornecido por DHCP com reserva na firewall ajuda a manter a numeração estável, mas não torna instantânea a atribuição do IP depois de um corte de energia. O switch, a firewall, a negociação Ethernet ou o próprio DHCP podem demorar a ficar disponíveis.

4. Recuperação imediata, sem reinstalar nada

Uma vez que o IP tenha sido obtido, os containers podem ser iniciados individualmente e os seus registos analisados. Esta abordagem é preferível a apagar volumes, recriar imagens ou reiniciar a máquina repetidamente.

ip -br addr
# Confirmar que a interface física já possui o IPv4 pretendido

docker start mosquitto
docker logs --tail 30 mosquitto

docker start zigbee2mqtt
docker logs --tail 60 zigbee2mqtt

docker start uptime-kuma smokeping phpipam-web

docker ps -a --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
Separar o problema de rede do problema Zigbee: o Zigbee2MQTT também depende do broker MQTT e da ligação ao coordenador Zigbee, situado noutra VLAN. Mesmo que o Docker e o IP estejam corretos, a aplicação pode falhar se o coordenador ou o broker estiver indisponível. É necessário consultar docker logs zigbee2mqtt para confirmar.

Estes comandos fazem parte do procedimento de recuperação recomendado. Os registos apresentados confirmam a identificação da causa de vários bindings, mas não constituem prova de que todos os containers tenham recuperado integralmente após esta sequência.

5. Alteração persistente: esperar pela rede certa

A solução foi preparada em duas camadas. Primeiro, corrigiu-se o serviço do Armbian que espera pela rede. Depois, acrescentou-se ao Docker uma verificação explícita do IPv4 antes de lançar o daemon.

Camada A · systemd-networkd-wait-online

Foi criado um drop-in em /etc/systemd/system/systemd-networkd-wait-online.service.d/ para aguardar especificamente pela Ethernet end0, com IPv4 e um prazo de 90 segundos.

# Ficheiro: /etc/systemd/system/systemd-networkd-wait-online.service.d/zz-wait-end0.conf
[Service]
ExecStart=
ExecStart=/lib/systemd/systemd-networkd-wait-online --interface=end0 --ipv4 --timeout=90

Um detalhe importante do caso: o Armbian já tinha outro ficheiro de configuração chamado armbian-any-interface.conf, que mantinha o comando --any --timeout=20. A primeira tentativa de criar 90-timeout.conf não prevaleceu, devido à ordem alfabética dos ficheiros de substituição. A mudança para zz-wait-end0.conf fez com que a nossa diretiva fosse a última aplicada.

systemctl daemon-reload
systemctl show systemd-networkd-wait-online.service -p ExecStart --no-pager
Verificação efetivamente confirmada: a saída de systemctl show passou a mostrar --interface=end0 --ipv4 --timeout=90. Antes disso, ainda mostrava --any --timeout=20.

Camada B · bloquear o arranque do Docker até existir o IP

Foi criado um segundo drop-in, desta vez para docker.service. O Docker só tenta iniciar depois de encontrar o endereço IPv4 esperado em end0.

Nota de publicação: o IP seguinte é ilustrativo. Deve ser substituído pelo endereço real atribuído ao servidor antes de executar os comandos.

# Ficheiro: /etc/systemd/system/docker.service.d/20-wait-for-ip.conf
[Service]
ExecStartPre=/bin/sh -c 'until ip -4 -o addr show dev end0 | grep -q "inet 10.10.40.20/"; do sleep 2; done'
TimeoutStartSec=120

O ciclo consulta os endereços IPv4 de end0 de dois em dois segundos. Quando encontra o IP especificado, o processo termina com sucesso e deixa prosseguir o arranque do Docker. Se o IP não aparecer, o tempo de arranque do serviço limita a espera.

systemctl daemon-reload
systemctl cat docker.service | tail -20
systemctl show docker.service -p ExecStartPre --no-pager
Verificação efetivamente confirmada: o systemctl cat listou o ficheiro 20-wait-for-ip.conf e o systemctl show reconheceu a diretiva ExecStartPre. Não foi necessário reiniciar o Docker para validar que o systemd tinha carregado a definição.
Limite importante: se a rede não ficar pronta dentro do prazo, o arranque do Docker poderá falhar. A unidade tem política de reinício, mas a recuperação automática após expirar o ExecStartPre não foi ainda comprovada. É necessário verificar este comportamento num ensaio controlado. Nunca alterar uma configuração de arranque sem manter acesso local ao equipamento.

7. Próximo passo: um teste de arranque controlado

As alterações foram carregadas pelo systemd, mas não houve ainda um reinício completo com observação contínua dos serviços. Antes de declarar a avaria resolvida, o procedimento de teste deverá incluir:

  1. Confirmar que existe backup das configurações e acesso local ao Banana Pi.
  2. Registar o estado dos oito containers com docker ps -a.
  3. Num momento adequado, fazer um reinício controlado e medir quando end0 recebe o IP.
  4. Verificar systemd-networkd-wait-online e docker.service com systemctl status e journalctl -b.
  5. Confirmar que os containers iniciam automaticamente e que os serviços respondem nas portas esperadas.
  6. Validar separadamente o Mosquitto e a ligação entre Zigbee2MQTT e o coordenador.
  7. Se o IP não for atribuído, verificar se o Docker volta a tentar ou permanece em falha.
# Recolha de evidência depois do próximo arranque
systemctl status systemd-networkd-wait-online docker --no-pager
journalctl -b -u systemd-networkd-wait-online -u docker --no-pager -n 100
networkctl status end0
docker ps -a --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"

Se o servidor depender de uma firewall, de um switch ou de uma UPS, é especialmente útil observar um arranque em que esses equipamentos também precisem de recuperar. É precisamente nesse cenário que aparecem as diferenças entre “a rede está ligada” e “a rede está pronta para os serviços”.

8. Porque este caso é interessante para aprender redes

O incidente reúne vários assuntos frequentemente estudados em separado: DHCP, serviços Linux, systemd, redes Docker, publicação de portas, dependências, monitorização e recuperação após falha elétrica. Na prática, todos se encontraram no mesmo problema.

DHCPO IP fixo por reserva pode chegar tarde
systemdOrdem de arranque não é sinónimo de disponibilidade
DockerUm container pode falhar antes de executar a aplicação
LogsA mensagem exata aponta para a causa

Lição essencial: quando vários serviços falham juntos, procurar primeiro aquilo que partilham — energia, rede, armazenamento, DNS ou dependências — costuma ser mais produtivo do que reinstalar cada aplicação. Aqui, a pista decisiva não foi o estado Exited (255) isoladamente, mas sim bind: cannot assign requested address.

Estado do caso em 13/11/2026: causa muito provável identificada; configurações de espera pela rede e de pré-arranque do Docker aplicadas e reconhecidas pelo systemd; recuperação automática completa ainda por validar num próximo arranque.
